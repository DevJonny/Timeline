# AGENTS.md

This file provides guidance to AI coding agents (Antigravity, Cursor, Windsurf, Claude Code, etc.) when working with code in this repository.

## Commands

```sh
npm run dev                       # http://localhost:5173/Timeline/
npm run dev -- --host             # expose on LAN to test on a real phone
npm run build && npm run preview  # the only way to exercise the service worker
npm run validate                  # data integrity (CI gate)
npm run check                     # svelte-check — runs with --fail-on-warnings
npm test                          # vitest
npm run icons                     # regenerate PWA icons; output is committed

npm run brief -- /tmp/b/BRIEF.md          # research brief, generated from live data
npm run merge-staged -- /tmp/b            # merge staged agent output; --apply to write

npm run brief -- /tmp/b/BRIEF.md --focus roman-empire   # same, for a focused timeline
npm run merge-staged -- /tmp/b --focus roman-empire

npx vitest run tests/ticks.test.ts          # one file
npx vitest run -t "no granularity hole"     # one test by name
npx vitest                                  # watch mode
```

CI runs validate → check → test → build on every push to `main`, then deploys
to GitHub Pages. All four must pass.

## Architecture

Client-side only: a single Svelte 5 page, no router, no SSR, no server. Content
is data — `public/data/entries.json` is an index; each entry's prose lives in
`public/data/details/{id}.json` and is fetched lazily on selection.

There are two kinds of timeline, rendered by the same component. The main one
spans 3.3 million years. A **focused timeline** covers one subject — see
"Focused timelines" below.

### Five things that will bite you

**1. Two year conventions.** Data is authored *historically* (`-3300` is 3300
BCE, and **there is no year 0**); the axis needs a *continuous astronomical*
coordinate (1 BCE is 0). `src/lib/time.ts` owns both. Everything entering the
axis goes through `toDecimalYear`; everything shown to a human comes back
through a `format*` function. Never render a raw axis coordinate.

Year ticks must be generated by iterating *historical* years and converting
back, or they render "3501 BCE" instead of "3500 BCE".

**2. The zoom transform stays in data space.** `src/lib/scale.ts` never
CSS-transforms content. At k up to 1e7 a translate offset exceeds 1e10px and
browsers lose sub-pixel fidelity. Positions are recomputed from a rescaled
domain each render.

`transformForDomain` is the inverse of that rescale and is the single function
behind *every* navigational affordance — zoom-to-extent, saved default view,
era-rail jumps, deep links, and preserving the range across rotation. Breaking
it breaks all of them at once.

**3. The render pipeline order matters.** In `Timeline.svelte`, per render:

```
filter (filter.ts) → importance gate (lod.ts) → lane packing (layout.ts) → clustering (lod.ts)
```

The gate *relaxes* when a filter is active, so filtering reveals more detail
rather than just thinning the view. Lane packing returns what does not fit as
`overflow`, which is exactly what clustering consumes. All four stages are pure
functions over arrays — test them directly, not through the DOM.

That relaxation is also where the dataset's scaling limit lives, not in file
size. `packLanes` compares each item against the occupants already in a lane,
so its cost grows with whatever survives the gate — and a broad filter both
matches more entries and relaxes the gate that would otherwise cull them.
Normal browsing never exercises this. Measure it with a filter matching a large
fraction of the dataset (at 211 entries, 87 matches re-render in ~15ms).

**4. `types.ts` must never import zod.** The app imports `TYPE_FAMILY` and
friends as runtime values, so anything `types.ts` pulls in lands in the browser
bundle. Validation lives in `schema.ts`, which is script- and test-only, and
carries `Assert<Eq<...>>` guards that fail compilation if the two drift.
Preference parsing in `prefs.ts` is hand-written for the same reason.

**5. Four colours carry seven types.** Markers of different types sit adjacent
arbitrarily, so the palette must clear the **all-pairs** colourblind test; no
subset larger than four passes. Two consequences are binding, not stylistic:

- every marker renders a **glyph** (dark-mode CVD warning is only legal with a
  secondary channel);
- every marker renders a **visible text label** (light-mode contrast triggers
  the relief rule).

Do not add a fifth hue without re-running a palette validator.

### Focused timelines

A focus is the same pipeline over a different dataset and a different domain:
`public/data/focus/{id}/` holds its metadata, entries and prose, and
`focus/index.json` is the menu. It **selects** the main entries belonging to its
period rather than copying them, so the main timeline growing grows the focus
too. Resolution is pure and lives in `src/lib/focus.ts`.

Four things about it are load-bearing:

- **`range` is the opening view; the domain is `range` ∪ everything in the
  focus.** An entry reaching outside the period widens the axis rather than
  being dropped — which is why `select.exclude` matters: one boundary-touching
  empire can double the axis and push the whole subject into a corner.
- **The domain is not stretched to `present`.** That is a main-timeline rule.
  An axis running from Augustus to today would leave the Roman Empire in the
  top fifth of the screen.
- **Zoom depth and the importance gate are both relative to the span.**
  `maxZoomFor` derives the ceiling from the domain so the deepest zoom always
  shows about four months, and `focus.gateScale` multiplies `k` before the gate
  reads it, so the same visible span earns the same detail in either timeline.
  Without that scaling a focus opens at gate 1 — a bare band. The two cancel
  exactly, which `tests/focus.test.ts` asserts.
- **Importance 1 inside a focus belongs to its chapters** — its own `age` spans,
  which become the era rail. Elsewhere importance 1 is closed.

A focus's filters are component-local and never persisted: carrying the main
timeline's filter into a focus would open it empty. Its `defaultView` is
likewise ignored. Both are main-timeline state about a different dataset.

The URL carries which focus is open (`#/f/{focus}`, `#/f/{focus}/e/{entry}`),
so Back leaves a focus for free, and `App.svelte` keys the timeline on the
focus id so no zoom transform or filter state survives the switch.

Detail prose resolves per *entry*, not per timeline: inherited entries keep
their prose in the main `details/` directory while a focus is open. That is
what `detailScope` in `Timeline.svelte` decides.

Use the `timeline-focus` skill to author one.

### Other cross-cutting rules

- **Base path.** The site is served from `/Timeline/`. Every runtime fetch of a
  `public/` file must go through `import.meta.env.BASE_URL`. A wrong path works
  in `dev` and 404s in production — only `preview` catches it.
- **The axis domain derives from *all* entries, never the filtered set.** If it
  shrank to fit a filter, the axis would rescale under the reader on every chip
  toggle. Selection is likewise resolved against all entries.
- **The search panel is the accessibility story.** The viewport is a
  `role="application"` canvas a screen reader cannot traverse. The panel is a
  real keyboard-navigable list of every entry. Nothing may be reachable only by
  pointing at the canvas.
- **Zoom transforms are published synchronously** from `zoom.ts`. Do not
  reintroduce rAF batching: Svelte already coalesces renders, and a previous
  in-flight guard could latch mid-mount, after which the view froze while d3
  kept updating underneath.
- **Persist preferences at the call site, not from an effect.** Svelte wraps
  `$state` objects in proxies, so a reference check against stored state never
  matches and an effect cannot tell a user edit from a restore — it will write
  defaults over saved values on mount.
- **`prefs` is the only copy of a preference, and `updatePrefs` the only writer.**
  `filters` is `$derived(prefs.filters)` for that reason. Storage is written
  whole, so a second copy of any field only has to go un-synced once: the next
  unrelated change spreads the stale copy back over what was saved. That is how
  saving a theme used to wipe the active search.
- **The default view is committed by its Save button; everything else applies
  live.** A year range is one value across two fields, so per-field commits
  necessarily persist half-written state — the first field alone cannot form a
  view, so it saves "no default view" and wipes what was there. Theme and
  motion are single values with immediate visible feedback and stay instant.
- **A form seeded from state must `untrack` what it seeds from.** The default-view
  inputs fill from `prefs.defaultView` on open. Read tracked, that effect
  re-runs on *every* preference write — including a theme change made while
  the sheet is open — and silently discards whatever is half-typed. Seed on the
  `open` transition only.
- **`bind:value` on `<input type="number">` yields `number | null`, never a
  string.** Empty fields and half-typed values (a lone `-`) arrive as null.
  State behind such a binding must be typed that way; string helpers like
  `.trim()` throw inside the derived, and the throw takes the save handler
  with it, losing the edit silently.
- **`controller` in `Timeline.svelte` is `$state`** so effects re-run once the
  zoom action is ready. As a plain variable, initial-view logic silently
  no-ops.

### Mobile-first constraints

Phones and tablets are the primary target. `touch-action: none` on the viewport
(or the browser claims the pinch first) plus cancelling iOS Safari's
non-standard `gesture*` events. `user-scalable=no` is deliberately **not** used.
`100dvh`, never `100vh`. No hover exists — prefetch on selection and focus.
Level-of-detail culling is what bounds DOM node count, so it is a performance
requirement rather than decoration.

## Adding content

Add an entry to `entries.json` plus a matching `details/{id}.json`, then run
`npm run validate` — it checks slug ids, real calendar dates, ordered ranges, a
detail file per entry with a matching id, and orphans. `importance` (1–5) is
the main authoring lever: it decides the zoom at which an entry appears. See
README.md for the field reference.

**Importance 1 is closed.** It is what renders when the timeline is fully
zoomed out, and it belongs to the ages and the few spans already holding it.
New content starts at 2.

To add a focused timeline, or entries to one, use the `timeline-focus` skill.
Its `focus.json` field reference is in README.md, and the rules that bite are
under "Focused timelines" above.

For bulk additions, use the `timeline-batch` skill: it researches subject areas
in parallel via `timeline-researcher` agents and merges centrally. Two rules
matter more than the rest. The brief is **generated** by `npm run brief`, never
hand-written or reused — it embeds the existing ids and keyword vocabulary, and
a stale copy tells agents to duplicate entries that already exist, which
nothing catches until merge. And every category gets an explicit list of
subjects owned by *other* agents, because the areas overlap far more than they
appear to.

## Scripts and Node

`scripts/*.ts` run under Node's **strip-only** TypeScript mode with no build
step, which rejects enums, namespaces, and constructor parameter properties.
Add `/// <reference types="node" />` for Node globals rather than putting
`node` in the shared tsconfig `types`, which would expose them to app code.

Local Node is 26; CI pins 24. Both support type stripping by default.

Relative imports use explicit `.ts` extensions (`allowImportingTsExtensions`).

## Verification caveat

`agent-browser` does not fire `requestAnimationFrame` in this environment,
headed or headless. Anything gated on a frame — d3 transitions, and therefore
animated `zoomTo` — will appear not to work. Setting the `motion: 'reduced'`
preference makes zoom synchronous and testable. Most bugs in this codebase were
found by driving the built app and inspecting the DOM, not by reading code.
